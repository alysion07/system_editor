
NodeInspector 재설계 아키텍처 제안서

문서 버전: 2.0
작성자: Gemini (Multi-Domain Design Expert)

1. 설계 철학 및 목표

현재 아키텍처는 UI, 데이터 구조, 유효성 검사, 파일 포맷팅 로직이 하나의 컴포넌트 정의 파일에 강하게 결합되어 있습니다. 이는 유지보수성과 확장성을 저해하는 요인이 됩니다.

새로운 아키텍처는 다음 철학을 기반으로 설계되었습니다.

* 관심사 분리 (Separation of Concerns):
    * 데이터 스키마 (The "What"): 컴포넌트가 어떤 속성을 갖는지 순수 데이터로 정의합니다. (UI나 로직 제외)
    * UI 렌더링 (The "How"): 스키마를 해석해 UI를 그리는 역할에만 집중합니다.
    * 비즈니스 로직 (The "Logic"): 데이터 유효성 검사 및 파일 포맷 변환 로직을 완전히 분리합니다.
* 선언적 UI (Declarative UI): UI는 데이터 스키마의 직접적인 결과물이어야 합니다. 스키마만 변경하면 코드를 거의 수정하지 않고도 UI가 변경되어야 합니다.
* 최고 수준의 확장성: 새로운 컴포넌트를 추가할 때, 복잡한 JS 코드가 아닌 간단한 데이터 스키마 파일 작성만으로 80%의 작업이 완료되어야 합니다.

2.1. 아키텍처 구성 요소

1. 컴포넌트 스키마 (Component Schemas)
    * 역할: 컴포넌트의 데이터 구조, UI 표현, 유효성 검사 규칙을 정의하는 순수 데이터 파일.
    * 형식: YAML 또는 JSON. (YAML은 주석을 지원하고 가독성이 높아 복잡한 규칙 정의에 더 유리합니다.)
    * 특징: JavaScript 로직(함수)이 전혀 포함되지 않습니다.
    * 위치: /src/schemas/components/SNGLVOL.yml

2. 스키마 레지스트리 (Schema Registry)
    * 역할: 애플리케이션 시작 시 모든 스키마 파일(/src/schemas/**/*.yml)을 읽어와 메모리에 저장하고, 요청 시 해당 스키마를 제공하는 중앙 관리자입니다.

3. UI 엔진 (`NodeInspector.jsx`)
    * 역할: "Dumb" 렌더링 엔진. 선택된 노드의 타입을 받아 레지스트리에서 스키마를 가져온 뒤, 스키마에 정의된 대로 컨트롤 라이브러리의 컴포넌트를 사용해 UI를 그립니다.
    * 특징: 특정 컴포넌트(SNGLVOL, PIPE 등)에 대한 지식이 전혀 없습니다.

4. 컨트롤 라이브러리 (Control Library)
    * 역할: 재사용 가능한 저수준(low-level) UI 컴포넌트 모음입니다.
    * 구성 요소: TextField, NumberField, SelectField, Checkbox, DynamicTable, 그리고 새롭게 정의될 FlagControl, ConditionalGroup 등.

5. 로직 엔진 (Logic Engine)
    * 역할: UI와 완전히 분리된 순수 비즈니스 로직 처리기입니다.
    * 구성 요소:
        * 유효성 검사 서비스: 스키마에 정의된 규칙(예: rules: { custom: 'validateVolume' })과 컴포넌트의 현재 데이터 값을 받아 유효성을 검사하고 결과를 반환합니다.
        * 포맷터 서비스: 전체 노드 데이터를 입력받아, 각 컴포넌트 스키마의 formatter 섹션을 참조하여 최종 SMART.i 형식의 텍스트 파일을 생성합니다.

3. 데이터 및 로직 흐름

1. UI 렌더링:
    1. 사용자가 SNGLVOL 노드를 선택합니다.
    2. NodeInspector는 SchemaRegistry에 SNGLVOL 타입의 스키마를 요청합니다.
    3. NodeInspector는 전달받은 스키마를 순회하며, fields 정의에 따라 Control Library에서 적절한 UI 컨트롤(TextField, FlagControl 등)을 렌더링합니다.
2. 실시간 유효성 검사:
    1. 사용자가 Area 필드의 값을 변경합니다.
    2. NodeInspector는 변경된 전체 데이터와 스키마를 ValidationService로 보냅니다.
    3. ValidationService는 validateVolume 같은 커스텀 규칙을 포함한 모든 규칙을 실행하고, 오류 메시지를 반환합니다.
    4. NodeInspector는 반환된 오류 메시지를 해당 필드 아래에 표시합니다.
3. 파일 생성:
    1. 사용자가 "파일 생성" 버튼을 클릭합니다.
    2. 애플리케이션의 전체 컴포넌트 데이터가 FormatterService로 전달됩니다.
    3. FormatterService는 각 컴포넌트의 스키마에 정의된 formatter 규칙(예: card_CCC0101: "'{compNum}0101 {area} {length} ...'" )에 따라 문자열을 조립합니다.
    4. 최종적으로 헤더, 전역 설정, 조립된 모든 컴포넌트 문자열을 합쳐 완전한 파일을 생성하여 사용자에게 제공합니다.

5. 결론

제안하는 아키텍처는 초기 설계 및 전환 비용이 발생하지만, 장기적으로는 유지보수성, 확장성, 안정성 측면에서 월등한 이점을 제공합니다. 개발자는 더 이상 복잡한 UI 로직에 신경 쓰지 않고, 데이터 스키마 정의라는 본질에만 집중할 수 있게 되어 생산성이 크게 향상될 것입니다. 이는
10배의 성장을 염두에 둔 시스템 아키텍트의 관점에서 가장 효율적이고 지속 가능한 설계입니다.
